### Money, time, rules

| # | Decision | Why |
|---|----------|-----|
| D-6 | **Integers only.** Money is integer cents (`…Cents`), rates are basis points (`…Bps`), time is epoch milliseconds in the engine and `timestamptz` in the database. One money module ported from LoanBook `src/ledger/money.ts` (`assertCents`, `assertBps`, `roundHalfUp(numerator, denominator)`); the buyer's premium is the only rounding in the project and it happens once, in `settle`. A non-integer at the boundary is refused with a typed error and never reaches the ledger. | LoanBook rules 4 and 5 |
| D-7 | **Rules are data in `rules/auction.v1.json`:** increment bands `[lo, hi)` in cents with the increment of the band containing the price; defaults for `soft_close_window_seconds` (120), `max_extension_seconds` (1800), `buyer_premium_bps` (1500). Each `Auction` row stores its own three settings (copied from the defaults at creation, editable until publish); the increment table is global in v1 (per-auction tables are P1). The file is content-hashed; the hash is recorded in D-23, checked by `rules:lint`, printed by `auction:eval`, and stored on every `Settlement` row. | Adjuster D1: a rule the code cannot express is a vocabulary change, not an `if` |
| D-8 | **Proxy bidding, exactly:** a bid is a maximum `M`. First bid: `M ≥ start` → leader, price = start. Otherwise the minimum is `price + increment(price)`; a bid under it is `REJECTED_BELOW_MINIMUM`. If `M > leaderMax`: new leader, price = `min(M, leaderMax + increment(leaderMax))`. If `M ≤ leaderMax`: leader unchanged, price = `min(leaderMax, M + increment(M))`, outcome `ACCEPTED_OUTBID`. The increment is taken from the band of the max it is added to, not from the band of the displayed price. Every accepted competitive bid strictly raises the price (brief §5 shows why). | eBay-style second price plus one increment, the convention most bidders already know; GB-01..GB-05, GB-23 |
| D-9 | **Ties go to the earlier sequence number.** An equal max is `ACCEPTED_OUTBID` at the full max. Sequence is assigned under the lock in arrival order; nothing random, nothing by timestamp (two bids can share a millisecond). | A tie rule a bidder can be told in one sentence; GB-04 |
| D-10 | **The leader may raise their own max** (`ACCEPTED_RAISE`): the max and the leader's winning seq move, the price and the close do not (O-6). A raise to the same or a lower amount is `REJECTED_NOT_ABOVE_OWN_MAX`. | A raise is not a competitive bid; extending on it would let a leader stretch their own auction. GB-06, GB-07, GB-11 |
| D-11 | **Reserve is a hidden floor**, null or at least the start price (a CHECK). Once the leading max is at or above the reserve, the price is at least the reserve (applied after the proxy rule, including on the first bid). The lot shows "reserve not met" as a boolean (O-5), never the amount. At close with the leading max under the reserve: `UNSOLD_RESERVE_NOT_MET`, no money. | Standard practice; GB-08, GB-09, GB-22 |
| D-12 | **Soft close, one rule:** a lot is open on `[opensAt, closesAt)`. After an accepted competitive bid at `now`: `closesAt ← min(now + W, scheduledEnd + cap)` when that is later than the current close; `extensionCount` increments. A bid at exactly `closesAt − W` changes nothing; one ms later extends by one ms. Extensions chain until `scheduledEnd + cap` and stop; a bid at or after `closesAt` is `REJECTED_LOT_CLOSED` and recorded. Own-max raises never extend (D-10). | A single comparison with no window check to disagree with it (found at kickoff: the first draft had two conditions and a golden that contradicted itself at the boundary). GB-10..GB-14, the chain in GB-12 |

### The bid path

| # | Decision | Why |
|---|----------|-----|
| D-13 | **One row, one lock: `SELECT … FOR UPDATE` on the lot's `LotState` row, READ COMMITTED, no retry loop.** `placeBid` runs one interactive transaction: lock the row → read `now()` → idempotency check → `applyBid` (pure) → insert the `Bid` row → update `LotState` → commit. Waiters queue on the row lock and each sees the committed state left by the one before. **Not optimistic locking** (a `version` column): under 50 writers in one second the losers retry against each other, the attempt count grows roughly with N², and each retry re-reads and re-judges; the row lock judges each bid once in arrival order. **Not an advisory lock** (Bookable D-24): Bookable needed a lock on a key because the first booker of a slot has no row to lock; here the state row exists from the moment the lot is created, the row lock is visible per lot in `pg_locks`, has no `hashtext` collision, and is released at commit or rollback like the advisory one. The advisory variant is a Phase 4 experiment on the same load script, not a product choice. **Not SERIALIZABLE**: the write set is one row and one insert, so serializability adds a 40001 retry path and buys nothing the row lock does not already give. `lock_timeout` is set to 5 s on the transaction (O-8); a timeout is `BID_TIMED_OUT`, retryable with the same idempotency key. Prisma's interactive-transaction timeout is raised above its 5 s default so a queued bid is not aborted by the client library. | Bookable's write path and its race tests, re-decided for a row that exists and a queue that must be ordered |
| D-14 | **Every well-formed attempt is one `Bid` row.** Columns: `lotId`, `seq` (gap-free, `bidCount + 1` under the lock, unique with `lotId`), `bidderId`, `maxCents`, `placedAt`, `idempotencyKey`, `outcome` (the closed set in `rules/auction.v1.json`), `accepted`, `priceBeforeCents`, `priceAfterCents`, `leaderBeforeId`, `leaderAfterId`, `closesAtBefore`, `closesAtAfter`, `extended`. Rejected attempts (`REJECTED_*`) are rows too, with before = after. `Bid` is append-only by trigger (UPDATE/DELETE refused); a void is a Phase 2 superseding row, never an edit. Boundary failures (non-integer amount, unknown lot, unregistered bidder, missing key) are refused before the transaction and write nothing. | "No lost bids" has to be checkable: N attempts, N rows. The before/after columns make the extension chain and every "why was I told X" readable without re-running anything |
| D-15 | **Time is injected and read under the lock.** `placedAt = now()` from `@/core/clock`, called after `FOR UPDATE` returns, once per bid. A client-supplied time is never read. Tests pin the clock (`advanceClock`) or pass `now` to the service. `auction:verify` checks `placedAt` is non-decreasing by `seq` within a lot. **Seam:** with more than one app process the clocks can disagree by their skew; this project runs one process and says so. A `clock_timestamp()` from Postgres inside the locked transaction is the Phase 4 alternative, measured, not assumed. | A bid that waited behind the lock must be judged at the time it was judged, not the time it was sent; Bookable's "the engine takes `now`" and Bracketry D-3 |
| D-16 | **`LotState` is a verified projection, not stored truth.** One row per lot, created with the lot: `priceCents`, `leaderBidderId`, `leaderMaxCents`, `leaderSeq`, `bidCount`, `acceptedCount`, `closesAt`, `extensionCount`. It exists so the hot path locks one row and judges a bid without re-folding the ledger under the lock. `auction:verify` recomputes the fold for every lot and fails on any column; the barrier test asserts the fold after every run. Nothing but `placeBid` writes it; a trigger refuses DELETE. This is a deliberate departure from LoanBook's "no balance columns": the departure is the point of the project, and the verifier is the price of it. | The card: many writers over one row. Without the row there is nothing to contend for |
| D-17 | **Idempotency is `(lotId, bidderId, idempotencyKey)`, unique, required.** The client generates a UUID per bid attempt and resends it on retry. Under the lock: a prior row with the same key and the same `maxCents` → return its outcome and seq with `replayed: true`, no new row; the same key with a different amount → `IDEMPOTENCY_MISMATCH` (409), no new row. The unique index backs the check so that a bug in the check cannot write a duplicate. The same key string from a different bidder is a different bid (the fixtures include one). | Ray's dropped connection; GB-18 and the REPLAY lots |
| D-18 | **The contention proof is a barrier test, not a sample.** `tests/contention/barrier.test.ts`: N raw `pg` clients (N ∈ {2, 10, 25, 50}; CI runs 25, O-10), each in its own transaction, all provably queued on the `LotState` row lock before the holder releases it (Bookable's `behindRowLock` pattern: poll `pg_locks` for `granted = false` until the count reaches N, never a timer), the clock pinned to `closesAt − 1000 ms`. After: `bidCount = N`, seq `1..N` with no gap, exactly one leader, `priceAfter` non-decreasing by seq, `LotState` equals the fold, `closesAt = (closesAt − 1000) + W` and `extensionCount` equals the number of accepted competitive bids whose `now + W` beat the close (with a pinned clock: 1), every `(bidder, key)` once; then every writer resends its key and the count is still N. The invariants are SQL in `src/auction/verify-sql.ts`, shared with `auction:verify`. A hang fails on a hard timeout; a "flaky" contention test is a broken one. | Bookable A-009 and spec §4.5; a `Promise.all` with a hopeful assertion is a flake generator |
| D-19 | **Throughput is measured by `scripts/load-bids.ts` and written to `docs/LOAD.md`**, never typed by hand: M concurrent writers (default 200) over L lots (default 4) in the last 10 s on the real clock through the real `placeBid`; prints accepted and rejected by outcome, bids per second, latency p50/p95/p99 ms measured around `placeBid` in the same process as the server code (no HTTP in Phase 1; Phase 3 adds the HTTP number beside it), max lock wait, then `os.cpus()[0].model`, core count, `os.totalmem()`, Node version, Postgres `version()`, the command line and the git SHA. `auction:verify` runs after and must be clean. A number in a screen, commit message or write-up names this file and its hardware line. | PRD goal 5; the owner's rule about numbers |
| D-20 | **`auction:verify` is the gate.** For every lot: V1 `LotState` equals the fold; V2 seq is `1..bidCount` with no gap; V3 the leader row exists, is accepted, and its bidder is the leader; V4 `priceAfter ≥ priceBefore` on every row, `priceBefore` of row k equals `priceAfter` of row k−1, rejected rows have before = after; V5 `closesAtAfter ≥ closesAtBefore`, chained the same way, never past `scheduledEnd + cap`; V6 `placedAt` non-decreasing by seq, accepted rows have `opensAt ≤ placedAt < closesAtBefore`; V7 no duplicate `(lotId, bidderId, idempotencyKey)`; V8 every `Settlement` equals `settle(fold)` and no settled lot has a later bid; V9 the rules hash on a settlement equals the current file's or the change is recorded here. Non-zero exit names the first lot and check. Runs in CI on every push and at the end of the barrier test and the load script. | LoanBook rule 7 |
| D-21 | **Lot status is derived:** `SCHEDULED` (`now < opensAt`), `OPEN`, `CLOSED` (`now ≥ closesAt`), `SETTLED` (a `Settlement` row exists). No status column; nothing sets a state by hand. Publish is the one staff action that changes a lot's timing (`opensAt`, `scheduledEnd`) and it is refused once the lot has a bid. | LoanBook rule 8; Bracketry's "computed on read" |
