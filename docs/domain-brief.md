# Gavel — Domain Brief (auctioneer and database-engineer review)

The source for vocabulary, the synthetic sales, the bid rules, the soft close, settlement, the invariants the verifier and the contention test check, the goldens and the kickoff measurements. Money is integer cents, rates are integer basis points, time is integer epoch milliseconds. Every rule in §5–§7 is implemented in `tools/auctionlib.py`; every worked example in §9 is printed by `tools/golden_answers.py` and ends with `OK`; every number in §10 is printed by `tools/reference_replay.py` on the frozen fixtures in §11. Items marked **[verify]** are one house's conventions, not facts; each has a D or O entry in `decisions.md`.

## 1. Product scope

Harlan & Pike Auctioneers (fictional) runs timed online auctions: an estate's contents, a county's surplus equipment. A sale has lots; each lot opens with its sale and closes at a scheduled time, staggered two minutes apart, unless late bids push it out. Bidders register once per house (a paddle number) and bid a maximum; the system bids for them up to it. When a lot closes the house settles it: who won, what they pay (hammer plus buyer's premium), or why it did not sell. The system's job ends at the invoice.

Left out: payment, real-time push, fraud and vetting, in-person clerking, media and shipping (PRD non-goals).

## 2. Vocabulary

Terms follow common US auction-house usage **[verify: houses differ on "hammer" vs "sale price" and on whether a soft close is called "extended bidding" or "anti-sniping"; the definitions below are Harlan & Pike's]**.

| Term | Meaning here |
|---|---|
| Auction (sale) | A set of lots with shared settings: soft-close window `W`, max extension `cap`, buyer's premium in bps. The org is the house; an auction belongs to it. |
| Lot | One item or group offered as a unit: start price, optional hidden reserve, `opensAt`, `scheduledEnd`. Catalog data; nothing on it changes once it has a bid. A withdrawal (D-73) is a separate row, set once, that closes the lot from that instant. |
| Start price | The least a first bid may be; the price shown after the first bid. |
| Reserve | A hidden floor. Not met: the lot does not sell. Met: the price is at least the reserve. |
| Max (proxy bid) | What a bidder submits: the most they will pay. Never shown to others. |
| Price (current bid) | What the leader would pay if the lot closed now: the second-highest max plus one increment, capped at the leader's max, floored at the reserve. |
| Increment | The step from the current price to the next minimum, by band (`rules/auction.v1.json`). |
| Minimum (next bid) | `price + increment(price)`, or the start price before any bid. |
| Leader | The bidder whose max is highest; on a tie, the one who bid first (lower seq). |
| Outbid | An accepted bid that did not take the lead. The price still moves. |
| Raise | The leader submitting a higher max. The price and close do not move. |
| Soft close | After a competitive bid at `now`, the close becomes `now + W` if that is later, up to `scheduledEnd + cap`. |
| Hard close | `scheduledEnd + cap`: the latest the lot can ever close. |
| Submission / attempt | One call to `placeBid`. Well-formed attempts become ledger rows whether accepted or rejected. |
| Seq | The lot's gap-free bid sequence number, assigned under the lock in arrival order. |
| Ledger | The append-only `Bid` table: every attempt with the state before and after it. |
| Lot state | The one row per lot the bid path locks and updates: price, leader, leader max, leader seq, counts, close, extension count. A projection of the ledger, verified. |
| Idempotency key | A client-generated UUID per attempt; a resend returns the original outcome. |
| Hammer | The price at close. |
| Buyer's premium | `roundHalfUp(hammer × bps / 10000)`, added to the hammer. |
| Settlement | The lot's outcome row: SOLD (winner, hammer, premium, total), UNSOLD_NO_BIDS, UNSOLD_RESERVE_NOT_MET, UNSOLD_WITHDRAWN (closed at the withdrawal, never sold). |
| Withdrawal | Staff pulling a lot before it closes (`LotWithdrawal`, D-73): one row with the reason, written under the lot's lock. The lot is CLOSED from `withdrawnAt`, every later attempt is `REJECTED_LOT_WITHDRAWN` (a row), and it settles `UNSOLD_WITHDRAWN`. Never sold, by correction either. |
| Invoice | Σ totals per bidder per auction, computed on read. Never paid here. |

## 4. The bid path

| # | Stage | Where | Decides | Output |
|---|---|---|---|---|
| 1 | Boundary | server action / route | `maxCents` is a safe positive integer, the lot exists in this org, the bidder is ACTIVE here, the key is present | Typed refusal, nothing written |
| 2 | Lock | transaction | `SELECT … FROM "LotState" WHERE "lotId" = $1 FOR UPDATE` (D-13); `lock_timeout` 5 s | The row, or `BID_TIMED_OUT` |
| 3 | Clock | transaction | `now()` from `@/core/clock`, read once, after the lock (D-15) | `placedAt` |
| 4 | Idempotency | transaction | A prior `(lotId, bidderId, key)` row? same amount → replay; different → mismatch (D-17) | Early return or continue |
| 5 | Engine | pure | `applyBid(lot, state, bidder, max, now, rules)` (§5–§6) | outcome, new state, before/after |
| 6 | Ledger | transaction | Insert `Bid` with `seq = bidCount + 1` and the before/after columns (D-14) | One row |
| 7 | Projection | transaction | Update `LotState` to the engine's new state (D-16) | One row |
| 8 | Commit | — | Lock released; the next waiter reads this state | Response: outcome, price, next minimum, leader?, closesAt, seq, replayed |
| 9 | Close | `auction:close --as-of` | `settle(lot, state, asOf)` for closed unsettled lots (D-22) | `Settlement` rows |
| 10 | Verify | `auction:verify` | §8 V1–V9 over every lot | OK or the first failure |

The response never includes anyone's max, the reserve amount, or another bidder's identity beyond "you lead" / "you are outbid".

## 5. Proxy bidding (`rules/auction.v1.json`, D-8..D-11)

**Increments** (band of the price being stepped from): $0–99.99 → $1; $100–499.99 → $5; $500–999.99 → $10; $1,000–4,999.99 → $25; $5,000–9,999.99 → $50; $10,000–24,999.99 → $100; $25,000+ → $250. Bands are contiguous, start at 0, end open; increments non-decreasing; the loader refuses anything else.

**Minimum:** `start` before any bid; else `price + inc(price)`.

**Apply a bid `M` from `B` at `now`** (after the open/closed checks in §6):

1. `B` is the leader: `M > leaderMax` → `ACCEPTED_RAISE`, `leaderMax = M`, `leaderSeq = seq`, price unchanged; else `REJECTED_NOT_ABOVE_OWN_MAX`.
2. `M < minimum` → `REJECTED_BELOW_MINIMUM`.
3. No leader → `ACCEPTED_LEAD`, price = start, leader = B, leaderMax = M.
4. `M > leaderMax` → `ACCEPTED_LEAD`, price = `min(M, leaderMax + inc(leaderMax))`, leader = B, leaderMax = M, leaderSeq = seq.
5. `M ≤ leaderMax` → `ACCEPTED_OUTBID`, price = `min(leaderMax, M + inc(M))`, leader unchanged. Equal max is this case: the price becomes the full max and the earlier bidder keeps the lead.
6. Reserve floor (any accepted outcome): if the lot has a reserve and `leaderMax ≥ reserve` and `price < reserve` → price = reserve.

Every row, accepted or rejected, takes the next `seq`.

**Why every accepted competitive bid raises the price.** Case 4: `price ≤ leaderMax < M` and `leaderMax + inc > price`, so the new price exceeds the old. Case 5: `M ≥ minimum = price + inc(price)` so `M + inc(M) > price`; and `leaderMax > price` (if `leaderMax = price` the minimum would exceed `leaderMax`, contradicting `M ≤ leaderMax`), so `min(leaderMax, M + inc(M)) > price`. Only a raise (case 1) leaves the price alone, which is why only raises never extend (§6). The verifier's V4 is this proof as SQL.

**Which band the increment comes from.** Case 4 adds `inc(leaderMax)`, case 5 adds `inc(M)`: the band of the amount being stepped from, not of the displayed price. GB-23: price 49,800 and a new max of 60,000 give 50,300 (49,800 + 500), and the next minimum is 51,300 (50,300 + 1,000). A house that steps from the displayed price would say the same here but differ when the price sits in a lower band than the max; O-2 is where that goes.

## 6. Soft close (D-12, D-15, D-21)

Status is derived: `SCHEDULED` while `now < opensAt`; `OPEN` on `[opensAt, closesAt)`; `CLOSED` once `now ≥ closesAt`; `SETTLED` when a settlement row exists. A bid while SCHEDULED is `REJECTED_LOT_NOT_OPEN`; while CLOSED, `REJECTED_LOT_CLOSED`; both are rows. **Withdrawn (D-73):** a lot with a `withdrawnAt` is `CLOSED` from that instant whatever `closesAt` says, even while it would still have been SCHEDULED; an attempt at or after `withdrawnAt` is `REJECTED_LOT_WITHDRAWN`, checked before the open and close checks, and is a row. `closesAt` does not move, because no accepted bid can follow the withdrawal.

After an accepted competitive bid (cases 3–5) at `now`: `newClose = min(now + W, scheduledEnd + cap)`; if `newClose > closesAt` then `closesAt = newClose` and `extensionCount += 1`, and the row records `extended = true`. One comparison: a bid at exactly `closesAt − W` changes nothing, one ms later extends by one ms, a bid one second before the hard close extends to the hard close, and the next one at `hardClose − 1 s` is accepted without extending. A raise never extends.

`now` is the injected clock read after the lock. The client's clock is never consulted; the lot page shows a countdown computed from the server's `closesAt` and re-polls.

## 7. Settlement (D-22)

`settle(lot, state, now)`: `null` while OPEN or SCHEDULED. CLOSED: withdrawn → `UNSOLD_WITHDRAWN` with `closedAt = withdrawnAt` and zero amounts, whatever the ledger says (D-73); no leader → `UNSOLD_NO_BIDS`; reserve not met → `UNSOLD_RESERVE_NOT_MET`; else `SOLD` with `winner = leader`, `winningSeq = leaderSeq` (the leader's latest max row: the raise, if they raised; the lead-taking row is the first accepted row after which `leaderAfter` is the winner, readable from the ledger), `hammer = price`, `premium = roundHalfUp(hammer × premiumBps, 10000)`, `total = hammer + premium`, `closedAt = closesAt`. Unsold outcomes carry zero amounts and no winner. The row stores the rules hash it was computed under.

## 8. Invariants (what `auction:verify` and the contention test check)

All in SQL over one lot, in `src/auction/verify-sql.ts`, shared by `auction:verify`, the barrier test and the load script's epilogue.

| # | Invariant |
|---|---|
| V1 | `LotState` equals `fold(ledger)` on every column (price, leader, leader max, leader seq, bid count, accepted count, close, extension count) |
| V2 | `seq` is exactly `1..bidCount`: `count(*) = max(seq)`, `min(seq) = 1`, unique `(lotId, seq)` |
| V3 | Exactly one leader: `leaderSeq` names an accepted row whose `bidderId` is `leaderBidderId`; null both or neither |
| V4 | Price chain: every row `priceAfter ≥ priceBefore`; `priceBefore(k) = priceAfter(k−1)`; rejected rows and raises have equal before and after; accepted competitive rows have `priceAfter > priceBefore` |
| V5 | Close chain: `closesAtAfter ≥ closesAtBefore`; `closesAtBefore(k) = closesAtAfter(k−1)`; `closesAtAfter ≤ scheduledEnd + cap`; `extended` iff the close moved; `extensionCount` = count of `extended` |
| V6 | Time: `placedAt` non-decreasing by `seq`; accepted rows have `opensAt ≤ placedAt < closesAtBefore`; `REJECTED_LOT_CLOSED` rows have `placedAt ≥ closesAtBefore`; accepted rows have `placedAt < withdrawnAt`, and `REJECTED_LOT_WITHDRAWN` rows need a withdrawal and have `placedAt ≥ withdrawnAt` (D-73) |
| V7 | No duplicate `(lotId, bidderId, idempotencyKey)` (the unique index, re-checked) |
| V8 | Every `Settlement` equals `settle(fold(ledger), asOf = closedAt)` on every field; no settled lot has a row with `seq > bidCount` at settlement; a settled lot has `closesAt ≤ closedAt`, or is withdrawn with `closedAt = withdrawnAt` and `UNSOLD_WITHDRAWN` (D-73) |
| V9 | The rules hash on every settlement equals `rules/auction.v1.json`'s, or the change is in `decisions.md` D-23 |

**The contention proof (D-18).** A lot with `closesAt = T`, the clock pinned to `T − 1000 ms`, N raw `pg` clients each holding a distinct bidder and a distinct max above the minimum. A holder connection takes `FOR UPDATE` on the `LotState` row first; the N clients start their `placeBid` calls; the holder polls `pg_locks` until N row-lock waiters are `granted = false`, then commits. All N then run in lock order. Afterward V1–V7 hold, `bidCount = N`, exactly one leader, `closesAt = T − 1000 + W` with `extensionCount = 1` (the first accepted competitive bid extends; every later one computes the same `newClose` and does not), and `acceptedCount` equals the number of maxes that were at or above the minimum at their turn. Then every client resends its key: still N rows, every response `replayed: true`. Then `auction:verify` is clean and `pg_stat_activity` is back to its pre-test count. No `setTimeout`, no sampling, a hard timeout so a hang fails.

**The measurement (D-19).** `scripts/load-bids.ts` on the real clock: M writers (default 200) over L lots (default 4) with `scheduledEnd` ten seconds out, each writer submitting until its lot closes; prints the outcome counts, bids per second over the whole run, latency p50/p95/p99 ms measured around `placeBid`, max lock wait from `pg_stat_activity.wait_event`, then the hardware block (CPU model, cores, memory, Node, Postgres `version()`, git SHA, command line) into `docs/LOAD.md`. The kit records no number from it; the first run on the Mac is the first number.
